## Как воспроизвести результат

1. `pip install -r requirements.txt`
2. Убедиться, что `data/train.parquet`, `data/benchmark_items.parquet`, 
   `data/benchmark_queries.parquet` на месте.
3. Открыть `notebooks/hybrid.ipynb`.
4. `Kernel → Restart & Run All`.
5. В `final_output/answer.csv` появится файл, идентичный отправленному на платформу.

Если `notebooks/emb_cache/` отсутствует — первый прогон закодирует корпус 
(1.5–2 ч на CPU). На GPU (Colab) это 3–5 мин.

Для сравнения с baseline: `notebooks/baseline.ipynb` → `baseline_output/answer.csv`.

## Подход

Каждое объявление получает итоговый рейтинг, который складывается из четырёх сигналов:

```
score = (BM25 + DENSE_W · dense + CAT_W · cat) · (1 + loc · LOC_W) + POP_W · pop
```

**Разбор формулы:**

- **(BM25 + DENSE_W · dense + CAT_W · cat)** — базовая релевантность объявления: 
  текстовое совпадение (BM25), семантическая близость (dense), 
  совпадение категории (cat).
- **· (1 + loc · LOC_W)** — если локация совпала, то
  растёт пропорционально. Не совпала, то рейтинг остаётся тем же.
- **+ POP_W · pop** — небольшая добавка за популярность.

| Сигнал | Роль |
|---|---|
| **BM25** | Совпадение слов (лексика) |
| **dense** | Близость по смыслу (эмбеддинги) |
| **cat** | Совпадение категории — **отключено** |
| **loc** | Совпадение локации — входит множителем |
| **pop** | Популярность объявления |

**Веса финальной версии:**

```python
DENSE_W = 0.6        
CAT_W   = 0.0        
LOC_W   = 1.0       
POP_W   = 0.2   
```
## Данные и признаки

### Входные файлы

Все данные лежат в `data/`:

| Файл | Что содержит | Для чего используется |
|---|---|---|
| `train.parquet` | ~500k Пары «запрос — объявление, которое пользователь выбрал» 
| `benchmark_items.parquet` | ~189k объявлений — база объявлений, по которой ищем 
| `benchmark_queries.parquet` | Список запросов, для которых нужен ответ 

### Признаки, которые использует модель

**1. Текстовые (для BM25)**

Собираем в строку из трёх полей объявления:

- `item_title_raw` — дублируется дважды: заголовок хорошо описывает 
  объявление, и совпадение с запросом в нём важнее, чем где-то в середине описания;
- `item_infm_params_text` — характеристики;
- `item_description_raw` — обрезается до 300 символов, чтобы не размывать индекс 
  редкими словами из хвоста описания.

Текст лемматизируется через `pymorphy3` (приводится к начальной форме: «бани» → 
«баня») и токенизируется `[a-zа-яё0-9]+`. Лемматизация обязательна: 
без неё BM25 считает формы слова разными словами и теряет совпадения.

**2. Плотные эмбеддинги (для dense)**

- Модель: `intfloat/multilingual-e5-small` (MIT, 384 dims).
- Формат входа: `passage: {title}. {params}` для объявлений,  `query: {query} {params}` для запросов.
- Вектора нормализованы, хранятся в float16.
- Кэш: `notebooks/emb_cache/` — по `item_id`, чтобы не пересчитывать при повторных запусках.

**3. Метаданные**

- `item_location_id == search_location_id` — совпадение локации. Один из сильнейших сигналов.
- `item_category_id == search_category` — совпадение категории. **Отключено** как неинформативное (см. раздел «Ошибки»).
- `log1p(item_rating_reviews_count)`, нормировано в 0..1 — популярность. Если несколько объявлений равны по тексту и локации — пользователи чаще выбирают популярные.

## Валидация

**Как построена:**

1. Из `train.parquet` берутся уникальные запросы. Ключ = 
   `search_query | search_location_id | search_is_delivery_search | search_infm_params_text | search_category`.
2. 15% ключей (но не больше 1000) уходят в валидацию.
3. Релевантные для запроса — все `item_id`, показанные по этому ключу в train.
4. В корпус добавляются объявления из `benchmark_items` — без этого плотность релевантных завышена, метрики нечестные.

**Метрика:** Recall@50 — доля релевантных объявлений, попавших в топ-50.

**Результаты на локальной валидации:**

| Конфигурация | Recall@50 |
|---|---|
| BM25 (baseline, `baseline.ipynb`) | 0.885 |
| + dense (DENSE_W=0.6) | 0.905 |
| + локация (LOC_W=1.0) | **0.920** |

**Подбор весов** (детали в `hybrid.ipynb`, функция `run_experiments`):

- `dense_w ∈ {0, 0.3, 0.6, 1.0, 1.5}` → оптимум **0.6** (плато 0.4–0.6)
- `loc_w ∈ {0, 0.5, 1, 2, 4}` → оптимум **1.0**
  - `loc_w=0` катастрофичен: Recall падает до 0.544
- `cat_w ∈ {0, 0.1, 0.2, 0.4}` → **0** (сигнал неинформативен)
- `deliv_scale ∈ {0.25, 0.5, 1.0}` → не влияет (delivery-запросов почти нет)
- `k1 ∈ {1.0, 1.5, 2.0}`, `b ∈ {0, 0.1, ..., 1.0}` → различия **в пределах шума**

## Типы ошибок и что с ними сделано

**1. BM25 не ловит формы слова.** «Баня», «бани», «баню» — разные токены. 
Решение: лемматизация `pymorphy3` + кэш через `lru_cache`.

**2. Длинные описания засоряют индекс.** 
Решение: обрезаем `desc` до 300 символов.

**3. Несовпадение типов колонок** `search_category` (int64) 
vs `item_category_id` (object) — pandas молча возвращает `False`. Решение: 
`sanity_check_inputs` перед запуском (типы, формат ID, пропуски).

**4. Учёт категории бесполезен** В train категория совпадает **в 100%** 
случаев, в benchmark 2 категории покрывают 99% объявлений. Решение: 
`CAT_W = 0.0`.

**5. Локация при большом весе затмевает текст.** `LOC_W=8.0` хуже, чем `LOC_W=1.0`. 
Без локации Recall падает до 0.54. Решение: `LOC_W=1.0`

**6. Запросов с доставкой почти нет.** 12 строк из 500k. Решение: 
`DELIV_LOC_SCALE=1.0`, логика оставлена на будущее.

**7. Первая реализация BM25 была циклом по документам.** Классический 
`rank_bm25` считает рейтинг каждого документа отдельно, питоновским циклом — 
~1 сек на запрос при корпусе 500k. Решение: переписал BM25 на разреженной 
матрице `scipy.sparse`. Вклад каждого слова в каждый документ считается 
один раз при построении индекса, рейтинг запроса — сумма нескольких столбцов 
(~1 мс вместо ~1 сек, ускорение в 1000 раз).

**8. Тюнинг `k1/b` — шум.** Разница <1 п.п., «лучший» конфиг меняется при 
переходе с 500 на 1000 запросов. Решение: зафиксировали `k1=1.5, b=0.75`.

**9. Дефолты класса Python фиксируются при определении.** Переопределение 
переменных после класса не работает — два «одинаковых» скрипта давали 
разные `answer.csv`. Решение: все веса в блоке настроек вверху, без 
переопределений в конце.

**10. Валидация ≠ benchmark.** Оптимум на валидации (`LOC_W=1.0`) на 
при отправке хуже, чем `LOC_W=8.0`. Решение: финал выбран по результатам 
на платформе.

**11. Формат `answer.csv`.** Потеря ведущих нулей, лишний индекс, 
неправильный разделитель. Решение: `to_csv(index=False)`, `dtype=str`, 
пробел между ID, валидатор формата перед отправкой.

**12. Долгое кодирование эмбеддингов.** 1.5–2 ч на CPU. Решение: кэш 
`emb_cache/` по `item_id`
